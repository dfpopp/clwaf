02防护架构

两站部署于同一 CDN 边缘之后，防护体系均为「CDN → WAF → 源站」三层结构，能力差异全部来自后端 WAF 产品本身。

2.1 站点 A：单层强门禁

所有未通过验证的请求一律返回 468 与挑战页，由云端脚本完成环境采集与证明计算。从脚本静态特征可见，其采集面覆盖自动化标识、插件与 MIME 类型、图形栈、多媒体能力等多个维度，并主动探测本机调试通道作为自动化判据。

其判定采用多因子加权累加模型：数十项检测各自带权重，命中即累加，达到阈值后拒绝。这意味着单项高权重检测即可决定结果，不依赖某一项单独失效——这是它面对未知自动化手段仍能守住的结构性原因。

两站对纯代码爬虫的防御均为 100%，10 / 10 未放行。

站点 B 的处理方式值得一提：前 5 项（请求标识层面即可识别）返回 JS 挑战页；后 5 项（伪装到接近真实浏览器）则直接下发图形验证码页面，不再走 JS 挑战。这是服务端侧的判断——它识别出「请求声明像浏览器、但没有 JS 执行能力」，于是跳过无意义的挑战直接上验证码。

纯 HTTP 客户端无法完成验证码提交，因此同样未放行。这种分流处理既节省了挑战页的下发开销，也让攻击者的成本从「执行 JS」升级为「识别验证码」。

04程序控制浏览器防御

程序控制浏览器指通过自动化框架驱动真实浏览器内核的采集方式。此类爬虫具备完整 JS 引擎，理论上可完成任何挑战计算，因此 WAF 必须依赖「环境或驱动特征异常」来识别。这是本维度最具威胁、也最能拉开差距的测试项。

06绕过对抗

绕过对抗检验的是架构层面的健壮性：当攻击者不正面突破检测规则，而是设法让请求以「WAF 未检查的形态」抵达源站时，防护是否仍然成立。

本次设计了 19 项主流手法，覆盖路径规范化差异、编码变形、HTTP 方法变换、协议降级四个方向。判定依据是响应是否抵达源站——通过响应头中的服务端特征变化来确认。具体路径构造不在公开版中列出。

同样是 0%，含义并不相同。

站点 A 的 0% 靠"不做区分"换来。它对所有未验证流量一视同仁，正常访客和攻击者享受同样待遇。所以不存在"误判"，代价是所有正常访问都被推迟，静态资源也不例外。

站点 B 的 0% 是在"做了区分"之后仍然不误拦。它保留了流量分类，判过之后依然没有冤枉任何一个正常样本。连「某个数据库查询语句怎么写」「某个弹窗怎么关」这类天然含敏感词的正常提问，也全部正确放行。

后者的难度明显更高：既要拦住攻击，又要理解关键词出现在自然语言里和构成攻击语法是两回事。
