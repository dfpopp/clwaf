WAF 挑战通用协议，不区分 JS 挑战或滑块验证。
接入前提：先在「站点设置 → API 接口路径」登记 App 的 API 路径前缀（如 /api/）。未登记时，无凭证请求会被当作普通网页返回 HTML 挑战页，App 无法解析。
接口通道响应协议：接口请求永远不返回 HTML 页面。凡不是业务响应，一律是「HTTP 状态码 + JSON」：code 与 HTTP 状态码相同、action 说明场景、page_url 是可交给 WebView 打开的引擎自产页面地址。不要把响应体交给 WebView 展示，也不要把 HTML 当业务数据解析——用业务请求的同域名拼接 page_url 打开 WebView 即可。状态页本身恒返回 200（状态由 URL 的 kind 表达），避免部分 WebView 遇到 4xx/5xx 直接显示浏览器错误页而不渲染页面内容。
下面路径里的 waf 是「系统设置 → 引擎接口前缀」（默认 waf，可改）。客户端一律以响应体里的 page_url / init_url / status_url / poll_url / base_prefix 为准，不要写死路径。
1 收到 428：需要挑战
App / 小程序请求 API 时若无有效凭证，WAF 返回 HTTP 状态码 428（Precondition Required），响应体是 JSON 且其中 code 同样是 428——HTTP 状态码与 body code 都是 428，不是只有其中一个。
响应体：{"code":428,"action":"challenge","challenge":true,"type":"...","reqID":"...","page_url":"/waf/challenge/init?reqID=...","init_url":"/waf/challenge/init?reqID=...","verify_url":"/waf/challenge/verify","status_url":"/waf/challenge/status?reqID=...","cookie_name":"...","base_prefix":"/waf"}。
428 的 page_url 与 init_url 相同，客户端统一按「遇到状态码 → 打开 page_url」处理即可，不必为 428 单写一套分支。挑战 ID 是响应体的 reqID（同时作为 init_url / status_url 的查询参数），没有 Challenge-Id 响应头。
2 打开 WebView 完成挑战
用 WebView 加载响应体的 init_url，即 GET /{prefix}/challenge/init?reqID={reqID}；同时按 status_url 轮询 GET /{prefix}/challenge/status?reqID={reqID}。查询参数名是 reqID，不是 id。
status 接口 HTTP 状态码恒为 200，结果看响应体：{"code":200,"status":"pending"} 继续轮询；{"code":200,"status":"completed","token":"...","cookie_name":"..."} 验证通过；{"code":404,"status":"expired"} 会话已过期，重新发起 API 请求取新 428；{"code":400,"status":"invalid"} 未带 reqID。
3 写 Cookie 并重试请求
status 返回 completed 后关闭 WebView，把 token 按 cookie_name 写入 Cookie，重试所有 API 请求。Cookie 在有效期内（系统设置「凭证有效期」，站长可配）免重复挑战；过期后自动重新走第 1 步。多个 API 同时收到 428 时只拉起一个 WebView，其余等 completed 后一起重试（WAF 不发 202）。
接口通道状态码总表（每一项都是「HTTP 状态码 + JSON」；code 恒等于 HTTP 状态码，page_url 一律是引擎自产页面相对地址，用站点域名拼好后交给 WebView 打开）：
场景 HTTP 状态码 body code / action page_url 的 kind App 怎么处理
需要人机验证 428 428 / challenge 挑战页（page_url = init_url） WebView 打开 page_url，按 reqID 轮询 status_url；completed 后写 Cookie 重试（上面三步）
进入等候室（基线 / 应用级 / CC 规则触发） 429 429 / waiting_room waiting（带 queue_id） WebView 打开 page_url 展示排队；同时原生轮询 poll_url，见下方「排队怎么结束」
CC 限速（浏览器页面内子请求） 429 + Retry-After 429 / rate_limited block（可不用） 原生提示「请求过于频繁」，按 Retry-After 等待后重试；App 登记 api_paths 后不会走这条，不必拉 WebView
规则拦截 403；限流型带 Retry-After 时 429 403 或 429 / blocked block WebView 打开 page_url；也可原生提示「访问被拒绝」。不要无限重试
队列已满 / 同时验证人数过多 503 503 / overload overload WebView 打开 page_url（「当前访问人数较多，请稍后重试」），稍后重试
源站不可用 502 502 / server_error error WebView 打开 page_url，稍后重试
页面内子请求无凭证（XHR/fetch） 428 428 / inpage_challenge_required 无（不建会话） 浏览器页面内的兜底响应，App 登记 api_paths 后不会遇到；重新发起业务请求即可，不要拉 WebView
排队怎么结束：429 / waiting_room 的响应体里除 page_url 还有 queue_id 和 poll_url（GET /{prefix}/waiting/status?queue_id=...）。WebView 只负责把排队页展示给人看，页面自己每秒更新排位；App 必须用原生网络层轮询 poll_url，拿到 {"code":200,"ready":true} 时该响应会下发等候室凭证的 Set-Cookie，把它同步进 App 自己的 Cookie 容器，再关闭 WebView、重试原 API 请求。只靠页面自己轮询不够：Android WebView / iOS WKWebView 的 Cookie 与 App 原生请求默认不共享，原生请求拿不到凭证会重新入队。
例外：CC 规则配了「跳转」时保持标准 HTTP 302 + Location（无 JSON body），客户端自行跟随或提示。所有状态页的 page_url 都是相对路径，且页面本身恒返回 200；状态语义看 kind，不要按 WebView 的 HTTP 码判断。
